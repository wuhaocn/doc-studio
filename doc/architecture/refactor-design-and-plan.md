# 在线文档系统重构设计与计划

## 1. 文档定位

本文档是 Memora 当前阶段的路线与实施计划文档。

它是以下事实的唯一来源：

- 阶段评估
- 里程碑
- 实施顺序
- 阶段门槛
- 风险与依赖

它不重复完整产品基线，也不重复完整技术基线。

---

## 2. 当前校验结论

### 2.1 当前真实状态

仓库已经从之前相对分散的方向收回到在线文档主线。

现在可以明确说：

- 主链路已经存在
- 可演示闭环已经存在
- 文档体系已经完成一次收敛
- 多租户、知识库、文档树、阅读/编辑、版本、知识库级权限已经形成基础骨架
- 真实用户、邀请、session、多工作区切换、统一搜索和状态页反馈已经形成 `P2` 基础版

仍不能明确说：

- 真实认证已经达到生产可用
- 系统已经适合正式生产上线
- 当前已经形成包含受控分发与机器接入的完整产品闭环
- 对外分享和程序化接入已经具备可信边界

### 2.2 闭环层次拆分

为了避免继续把范围做散，当前应把产品闭环拆成四层：

#### A. 主体进入产品闭环

- 管理员注册工作区
- 建立真实用户与租户主体
- 邀请成员加入
- 登录、登出、会话失效、刷新

#### B. 内部知识生产闭环

- 工作台
- 知识库
- 文档树
- 阅读 / 编辑
- 版本
- 搜索
- 删除恢复
- 权限反馈

#### C. 受控分发闭环

- 内部阅读直达
- 受控外部分享
- 公开发布

#### D. 机器接入闭环

- service account
- API key
- 作用域控制
- 文档 API
- 审计与吊销

当前代码状态已经覆盖 A，并完成 B 的基础闭环；C/D 仍未闭环。

### 2.3 默认实施决策

为了避免后续实现过程中不断摇摆，当前默认决策如下：

- `注册` 默认实现为 `Owner Signup`
- `分享` 默认实现为 `受控外部只读分享`
- `API Key` 默认实现为 `Service Account / API Key`
- `删除恢复` 默认实现为 `软删除 + 回收站 + 恢复`
- `KnowledgeBase` 继续作为当前主权限边界

当前不纳入本轮收口：

- 实时协作编辑
- 评论 / 批注
- AI 主入口
- 桌面同步
- 模板 / 标签 / 引用关系
- 面向公众的普通用户自助注册

## 3. 里程碑

| 里程碑 | 目标 | 完成定义 |
| --- | --- | --- |
| M0 | 方向统一 | 文档、模块职责、主流程口径统一 |
| M1 | Demo 主链路可运行 | 工作台、知识库、文档树、编辑、版本、最小权限可运行 |
| M2 | 主体与内部主链路收口 | 真实主体进入产品，内部主链路不再依赖 demo 身份 |
| M3 | 内部知识产品闭环 | 搜索、权限反馈、版本行为与状态反馈达到基础可用 |
| M4 | 治理与受控分发基线 | 审计、受控分享 / 发布达到基础可用 |
| M5 | 平台接入基线 | service account、API key、程序化文档操作达到基础可用 |

当前判断：

- `M0` 已完成
- `M1` 基本完成
- `M2` 已完成
- `M3` 基础版已完成，但仍未生产化
- `M4/M5` 基线已完成，但仍未生产化

## 4. 当前优先级

### 4.1 第一优先级

- 稳定多工作区切换、统一搜索、状态页与权限反馈
- 补主链路回归测试和人工冒烟
- 继续保持 canonical 文档与代码口径一致

### 4.2 第二优先级

- 审计模型与关键操作追踪
- 关键日志、回滚和排障能力

### 4.3 第三优先级

- 受控外部分享
- 发布状态与撤销
- 外部阅读路径与内链阅读路径分离

### 4.4 第四优先级

- service account
- API key
- 文档外部 API

### 4.5 第五优先级

- 搜索质量、索引化和排序优化
- 更强版本 diff 与恢复体验

## 5. 阶段计划

### 5.1 P0 底座收口

目标：

- 从“可演示”推进到“边界不自相矛盾”

重点：

- 修正跨知识库聚合读模型的权限继承
- 补齐删除 / 恢复语义
- 固定统一错误语义
- 补权限与聚合查询回归测试
- 更新 canonical 文档

退出标准：

- 聚合查询不会越过知识库权限边界
- 删除对象具备后续恢复所需的最小元数据
- 关键接口错误语义一致
- 权限相关主链路具备最小自动化回归

### 5.2 P1 身份与进入产品

目标：

- 让系统不再依赖 demo 主体进入产品

重点：

- 引入真实 `user`
- Owner Signup
- tenant invite / accept
- login / logout / refresh / session
- Web 身份流与会话流收口

退出标准：

- 新环境可由管理员自主创建工作区
- 普通成员只能通过邀请加入
- 后端主链路不再依赖 demo token
- 前端登出与会话失效具备真实行为

### 5.3 P2 内部知识产品闭环

目标：

- 把文档工作区推进到“可用的内部知识产品”

当前实现状态：

- 已完成多工作区切换基础版
- 已完成工作区统一搜索 V1
- 已完成阅读态 / 编辑态 / 禁止态状态页收口
- 已完成知识库页和文档页的更细权限反馈
- 已完成 P3 审计基线：关键操作写入、失败审计、最小查询、汇总导出和最近记录展示
- 已完成 P4 受控分享基线：文档级外部只读分享、访问码、过期 / 撤销与公开分享页
- 已完成 P5 平台接入基线：Service Account、API key、开放文档接口与并发版本保护
- 当前剩余重点转向搜索质量治理、会话治理和更细权限模型

重点：

- 搜索 V1
- 权限配置与错误反馈
- 版本行为收口
- 恢复冲突与状态反馈
- 阅读态 / 编辑态 / 禁止态的状态反馈

退出标准：

- 用户可在租户内稳定找到知识
- 管理员可清晰配置访问边界
- 删除与恢复可理解、可使用
- 版本与恢复行为不互相混淆

### 5.4 P3 治理与审计

目标：

- 让核心变更行为具备追踪能力

当前实现状态：

- `audit_log` 已作为基线模型落库
- 已覆盖注册、登录成功 / 失败、工作区切换、邀请、知识库和文档关键动作
- `GET /api/v1/audit-logs`、`/summary`、`/export` 已支持最小治理查询与导出
- Web 首页与知识库上下文面板已展示最近审计记录，首页已展示汇总和导出入口

当前限制：

- 当前失败审计仍只覆盖高风险边界，不追求所有业务校验分支
- 长期留存目前仍停留在 retention 配置与手动导出基线，尚无独立归档服务

重点：

- audit log 模型
- 主链路操作审计
- 最小查询能力

退出标准：

- 能追查谁改了什么
- 能追查谁删了什么
- 能追查谁恢复了什么
- 能追查谁改了权限

### 5.5 P4 受控外部分发

目标：

- 把内部阅读、受控分享、公开发布正式拆成独立产品流

重点：

- 文档级受控外部分享
- 分享过期 / 撤销
- 受控阅读页
- 分享访问审计

当前实现状态：

- 文档阅读直达与受控分享已拆成两条链路
- 管理角色可从知识库详情、阅读页、编辑页创建和撤销受控分享
- 外部用户可经 `/share/:token` 只读访问授权文档

退出标准：

- 阅读直达与外部分享语义清晰分离
- 分享不会扩大工作区内其他内容可见范围
- 过期 / 撤销可立即生效

### 5.6 P5 平台接入能力

目标：

- 提供最小可信的机器接入能力

重点：

- service account
- API key 生命周期
- knowledge base 作用域
- 文档外部 API
- 并发保护与审计

当前实现状态：

- 已支持签发、轮换、禁用、吊销 API key
- 开放接口已支持列出知识库、列出文档、读取文档、读取版本、创建文档、更新文档
- `expectedVersionNo` 已作为并发保护基线

退出标准：

- API key 只能访问授权范围
- key 可创建、轮换、吊销、失效
- 程序化更新不会无意覆盖人工编辑结果

## 6. 阶段门槛

- `P4` 不得早于 `P1` 和 `P3`
- `P5` 不得早于 `P0` 和 `P1`
- `搜索 V1` 上线前必须先修掉聚合权限边界问题
- `分享` 与 `API key` 不得共用同一种 token 语义
- `版本历史` 不得被描述成 `删除恢复`

对外宣称“产品闭环已形成”的最低标准应是：

- 主体进入产品闭环成立
- 内部知识生产闭环成立
- 搜索可用
- 删除恢复可用
- 审计基础可用
- 权限边界清晰且可验证

## 7. 工作流拆分

### 7.1 Backend

- 真实主体与会话
- 聚合权限谓词
- 删除 / 恢复元数据
- 搜索接口
- 审计
- 分享接口
- API key 鉴权

### 7.2 Web

- 注册 / 登录 / 邀请接受
- 搜索入口与结果页
- 权限配置交互
- 回收站与恢复入口
- 分享状态反馈
- 会话失效与错误状态处理

### 7.3 Documentation

- 只维护 canonical 文档
- 根 README 与模块 README 保持入口摘要角色
- 不再新增“总结类”平行文档
- 每个阶段的默认决策和门槛必须回写到计划文档

## 8. 风险与依赖

### 8.1 主要风险

- 没有真实主体，注册 / 登录闭环始终只是演示
- 聚合查询如果不继承知识库权限，后续搜索和 API 会放大越权风险
- 没有恢复语义时，版本能力会被误当成删除恢复
- 把阅读链接描述成分享，会导致产品和安全边界继续混淆
- 把分享和 API key 混成一条能力线，会让人类访问模型和机器访问模型失真
- 如果文档再次分裂，产品与工程认知会再次漂移

### 8.2 主要依赖

- Backend Gradle 环境稳定
- Node 工具链稳定
- 前后端错误语义对齐
- 数据库 schema 可平滑升级

---

## 9. 当前阶段出口标准

当前直接目标应当是 `P0`。

当以下条件满足时，可视为 `P0` 完成：

- `GET /api/v1/documents` 等聚合查询不再绕过知识库权限
- 删除对象保留恢复所需元数据
- 权限 / 删除 / 冲突错误语义一致
- 文档、代码、测试对当前边界表述一致

当以下条件满足时，可启动 `P1` 主实施：

- P0 已完成
- 主链路测试可稳定执行
- 当前 demo 会话替换路径已经明确
